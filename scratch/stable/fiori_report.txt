### Selection Screen Design

| Program | Selection Screen Quality | Issues |
|---------|--------------------------|--------|
| `ZPROG_SFLIGHT_ALV` | ⭐⭐⭐ Good | Logical block grouping (B1), SELECT-OPTIONS for ranges |
| `ZPROG_SFLIGHT_FINAL` | ⭐⭐⭐ Good | Same as above |

| `ZPROG_EPM_DEMO` | ⭐⭐ Mixed | Uses inline COMMENT labels (good for readability), but bare SELECT-OPTIONS |

**`ZPROG_INVENTORY_MANAGER` — Critical UX Issue**: The program uses a single `p_action` parameter (values: C/D/A/R/M/X/L/S/E) to control behavior. This is a **1990s-era action code pattern** — confusing for users who must memorize single-character codes. The `AT SELECTION-SCREEN OUTPUT` / `MODIFY SCREEN` logic dynamically shows/hides blocks, which is UX improvement, but still opaque.

**XML Metadata (`zprog_inventory_manager.prog.xml`)**: Confirmed ABAP report type (`SUBC=1`), uses logical database `D$S`, and has bilingual text pool (English + German `Aktionsauswahl`). This confirms basic i18n awareness.

## 3. UX Quality of Current Programs

### User Experience Assessment

#### `ZPROG_SFLIGHT_ALV` / `ZPROG_SFLIGHT_FINAL`
- **Strengths**: Clean OOP structure, fast SQL (JOIN at DB level), informative error message on empty result
- **Weaknesses**:
  - No currency formatting for `price` field (displayed as raw number)
  - No date formatting for `fldate`
  - No drill-down to flight details
  - No export to Excel button (available via `set_all()` but not prominent)
  - Desktop-only (SAP GUI)

#### `ZPROG_INVENTORY_MANAGER`
**Most critical UX problems:**
1. **Action code UI-antipattern**: `p_action = 'C'/'D'/'A'/'R'` — user must know codes
2. **Display via WRITE**: The `DISPLAY_SINGLE_ITEM` form uses raw `WRITE:` statements with hardcoded column positions (col 12, 22, 30...) — breaks if field values exceed column width
3. **No ALV for list display**: `DISPLAY_INVENTORY_LIST` uses `WRITE:` with COLOR COL_HEADING — no sorting, filtering, or export
4. **FORM routines** (not methods): `FORM set_defaults`, `FORM modify_screen` etc. are pre-OOP style mixed with OOP class — inconsistent architecture
5. **Null reference risk**: Line 258 — `lo_inventory->get_all_inventory()` called when `lo_inventory` is not initialized (no `CREATE OBJECT`)
6. **No low-stock visual alert**: Low stock detection exists in `ZCL_INVENTORY_MANAGER->get_low_stock_items()` but list output gives no visual cue (color, icon)

### Missing UX Features (all programs)
- ❌ No F4 help / value help on key fields (carrier, material, plant)
- ❌ No dynamic title in ALV header
- ❌ No user-specific column layout persistence
- ❌ No print-optimized layout
- ❌ No mobile/tablet support
- ❌ No real-time validation feedback (only on selection screen submit)

## 5. Recommendations

### Quick UX Wins (Classic ABAP — no Fiori needed)

1. **`ZPROG_INVENTORY_MANAGER`**: Replace `p_action` parameter with a proper `RADIOBUTTON GROUP` — eliminates the action code memorization problem
2. **`ZPROG_INVENTORY_MANAGER`**: Replace all `WRITE:` display forms with `CL_SALV_TABLE` — consistent with the sflight programs, adds sorting/filtering/export for free
3. **`ZPROG_INVENTORY_MANAGER`**: Replace FORM routines with class methods — architectural consistency with `ZCL_INVENTORY_MANAGER`
4. **`ZPROG_SFLIGHT_ALV`**: Add `CL_SALV_COLUMN_TABLE->set_currency()` on `price` column using `currency` column as reference → proper currency display
5. **`ZPROG_SFLIGHT_ALV`**: Add F4 help via `SET_F4_ENABLED` on `carrid` SELECT-OPTIONS field

## Summary

The project is **100% Classic ABAP UI** with good OOP structure in the ALV programs and a well-designed data model in `ZINV_STOCK`. The `ZCL_INVENTORY_MANAGER` class is clean enough to serve as a RAP behavior handler with minor adaptation. The key gaps are the **complete absence of CDS views, OData services, and any Fiori artifacts**.

The infrastructure is ready: `VSP_FEATURE_UI5=on`, `VSP_FEATURE_RAP=on`, and all UI5 MCP tools (`ListUI5Projects`, `GetUI5Project`, `ReadUI5File`, `GetODataMetadata`, `TestODataService`, `GetCDSExposure`) are enabled and permissioned. The only tooling blocker is that `pkg/adt/ui5.go` is read-only (no write/deploy path yet).

**Recommended first action**: Run `ListUI5Projects` to inventory what Fiori apps already exist on the NPL system, then create the CDS view stack for `ZINV_STOCK` as the foundation for the first Fiori Elements app.
